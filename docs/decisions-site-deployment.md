# Decisions: deploying on the site server

Goal: run the app on the internal Windows server as one process on one port,
built from the same kit the team used for the ESG app (`E:\KPMG\KPMG_Server_req`,
used as a guide, not copied blindly). How to do it: `docs/DEPLOYMENT.md`.
What is not done yet: `docs/TODOS-for-Production.md`.

| # | Decision | Why | Alternatives rejected |
|---|----------|-----|-----------------------|
| D1 | One `uvicorn` process serves the API and the built website, on port **8199** (chosen by the user). | Matches the kit: no nginx or IIS, one thing to start and stop. Several apps share the server, so each needs its own port; ESG uses 8018. | A separate web server for the site: more to install and secure. |
| D2 | The website calls `/api` on its own address (no `VITE_API_BASE`). The zip builder strips that variable and refuses a `dist` containing `10.0.2.2` or a laptop address. | Same origin: no CORS, and the same build works on any hostname or IP. The Android build bakes in an address; mixing the two builds would point the site at the wrong server. | Bake the server address into the site: breaks when the host name changes. |
| D3 | `APP_ENV=production` (set by `start-server.bat`) closes `/docs` and CORS. A weak or missing `JWT_SECRET` only WARNS (changed on request: not a hard stop yet; tracked as P2). Development keeps the easy defaults. | A forgotten setting on the server cannot leave the API docs open, and the dev loop is unchanged. The secret rule was relaxed so a site install is never blocked by it. | Hard stop on a weak secret (first version): blocks installs until a 32+ character secret is set. Strict only if `.env` says so: a missing line silently means open. |
| D4 | Settings stay in `backend\.env` (the user asked to keep the `.env` files). `.env.example` lists every variable. The existing local `.env` is untouched. | Keeps secrets out of the code and out of the zips. | A config file in the repo; env vars set in Windows: harder to hand over. |
| D5 | Schema changes stay Alembic migrations that run when the server starts; `db-migrate.bat` runs them on their own. No `create_schema` script and no `seed` option in the scripts. | The app already works this way. `seed.py` makes demo users that all share the password `pass`. | Port the kit's `create_schema` / `seed` scripts: does not fit this app and invites running the seed on production. |
| D6 | `create_admin.py` is the only way to make the first account: random temporary password, printed once. | Without it a new server has no login. Required by the kit. | Seed an admin with a fixed password: guessable. |
| D7 | Access log to `backend\logs\app.log` (writes and failures only, no bodies or query strings). | Kit requirement; the first thing to read when something fails. Bodies carry passwords. | Log everything: huge and leaks secrets. |
| D8 | `requirements.txt` is runtime only; `requirements-dev.txt` adds pytest and httpx. | The server needs only the runtime set. | One file for both: installs test tools on the server. |
| D9 | Moved `psycopg2-binary` to 2.9.11, `pydantic` to 2.12.5 and `SQLAlchemy` to 2.0.44; left `fastapi`, `uvicorn` and `langchain-*` as they were. | Checked with `pip --dry-run --platform win_amd64 --python-version 3.14`: the old pins have no Python 3.14 wheel for `psycopg2-binary` or `pydantic-core`, so pip would try to compile them and fail. The other packages resolve. | Bump everything to latest: large regression risk with no way to test on 3.14 here. |
| D10 | Ship the prebuilt `frontend\dist` in every zip; no node on the server. `dist` stays gitignored. | The server often cannot reach the npm registry. Kit behaviour. | Build on the server: needs node and internet there. |
| D11 | A full release zip (`make-release.bat`) for first installs, and a patch zip (`make-patch.bat <commit>`) for updates. Both exclude `.env`, databases, logs, backups, `venv`, `node_modules` and the Android project. | A first install needs everything; an update needs only the changes. | Zip the folder by hand: easy to include `.env` or `node_modules`. |
| D12 | The Android app stays out of the server zips; its address and origin are handled by `VITE_API_BASE` and `CORS_ORIGINS`. | The phone app is built and shipped separately (`docs/ANDROID_APP.md`). | Bundle the project: adds a lot of files the server never uses. |
| D13 | The AI assistant stays off unless `GOOGLE_API_KEY` is set. | It sends questions and data to Google; that needs KPMG approval. Without a key the chat says it is not configured. | On by default: data leaves the network without anyone deciding. |
| D14 | Passwords: temporary password at creation, no forced change yet (P20). | The app has no change-password feature; adding one is its own piece of work and may be replaced by SSO. | Build it now: scope creep during deployment prep. |
| D15 | The full release zip includes a ready `backend\.env`, generated when the zip is built (fresh random `JWT_SECRET`, SQLite database). It is never the developer's own `.env`, and patch zips never contain a `.env`. Chosen by the user ("keep the .env"). | Turnkey install: nothing to hand-edit before the first start. A new secret per zip means no shared or dev secret ships. A patch cannot overwrite the server's settings. | Ship the dev `.env`: carries the dev secret and database. Ship none and let the installer create it: also works (the installer does that if it is missing) but the user asked for it in the zip. |
| D16 | `scripts\install.bat <login> [<email>]` does the whole first install and is safe to re-run (never overwrites `.env`, tables or admins). | One command with a named failing step instead of several commands to get right. | A longer checklist: easy to skip a step. |
| D17 | The database defaults to SQLite in the zip; PostgreSQL is a one-line switch. `db-migrate.bat` creates a missing PostgreSQL database (if the user may) and then every table. | The app runs with nothing else installed, while the kit's PostgreSQL route stays open. SQLite is a single file to back up. | PostgreSQL by default: the install fails until a database server and credentials exist. Note: the PostgreSQL path (database creation, migrations, dump and restore) has not been run on a real server. |
| D18 | The first admin's notify email is optional. | A login is all a person needs to sign in; the email only receives alerts. | Required email: blocks the install on a detail. |
| D19 | For a server that cannot reach PyPI, the Python packages ship as a separate zip of ready-built wheels (`make-wheelhouse.bat`), built for the server's exact Python version and platform. `setup.bat` and `update.bat` install from a `wheels\` folder when one exists, with `--no-index`. | The server's firewall blocked PyPI. A separate zip keeps the release zip small, and `--no-index` means pip never waits on or tries the network. The builder proves the set is complete before writing it. | Put the wheels in the release zip: 100+ MB for every install, even ones with internet. A proxy or internal mirror: simpler if one exists (still supported: set `HTTPS_PROXY` or `PIP_INDEX_URL`). |

## Open points for the site visit

- PostgreSQL host, port, database name and user (go in `backend\.env`).
- SMTP host and sender, if alert emails are wanted.
- Git clone or patch zips only (both are supported).
- Whether the phone app will use this server, and whether HTTPS is available (P21).
- Whether the AI assistant is allowed (D13).
